## Abstract

This HIP proposes a new `signer/v1` plugin type for extending Helm's provenance system with additional signing mechanisms. Unlike the built-in adapter approach (see alternative HIP), this proposal leverages Helm's existing plugin architecture to enable community-maintained signing plugins. Official plugins for GPG, Sigstore, Notary v2, and SSH would be maintained by respective teams, providing both trust guarantees and ongoing expertise.

## Motivation

### Why Plugins Over Built-in Adapters?

The alternative approach (built-in signing adapters) bakes specific signing implementations into Helm core. While simpler initially, this has drawbacks:

| Consideration            | Built-in Adapters         | Plugin Architecture      |
| ------------------------ | ------------------------- | ------------------------ |
| **Core binary size**     | Grows with each mechanism | Minimal core             |
| **Maintenance burden**   | Helm team maintains all   | Distributed to experts   |
| **Update velocity**      | Tied to Helm releases     | Independent releases     |
| **Community mechanisms** | Requires core changes     | Anyone can contribute    |
| **Air-gap distribution** | Always included           | Include what you need    |
| **Expertise alignment**  | Helm team must learn all  | Teams maintain their own |

### Expertise Alignment

Signing mechanisms are complex and evolving:

- **Sigstore**: Rapidly evolving ecosystem (Fulcio, Rekor, keyless)
- **Notary v2**: Enterprise trust policies, certificate chains
- **GPG**: Web of trust, keyserver integration
- **SSH**: Allowed signers format, certificate authorities

Each mechanism is best maintained by teams with deep expertise:

| Plugin            | Ideal Maintainer       | Rationale               |
| ----------------- | ---------------------- | ----------------------- |
| `signer-gpg`      | Helm team              | Existing implementation |
| `signer-sigstore` | Sigstore team          | Cosign library experts  |
| `signer-notary`   | Notary project         | notation-go experts     |
| `signer-ssh`      | Helm team or community | Standard crypto         |

### Trust Through Official Plugins

Provenance plugins are security-critical. Users must trust that:

1. The plugin correctly implements the signing algorithm
2. Private keys are handled securely
3. Verification cannot be bypassed

**Official plugins** maintained by responsible teams provide this trust:

```yaml
# Chart.yaml - using official Sigstore plugin
plugins:
  - name: signer-sigstore
    version: "1.2.0"
    repository: oci://ghcr.io/sigstore/helm-plugins/signer-sigstore
    type: signer/v1
```

The Sigstore team's reputation backs the plugin. Users can verify:

- Plugin is published by `sigstore` GitHub organization
- Signed by Sigstore's own signing infrastructure
- Audited alongside the cosign library

## Specification

### Plugin Type: `signer/v1`

A new plugin type for signing and verification:

```yaml
# plugin.yaml
apiVersion: helm.sh/plugin/v1
metadata:
  name: signer-sigstore
  version: 1.2.0
type: signer/v1
runtime: extism/v1 # Wasm (CLI) or go/v1 (SDK)

signer:
  # Mechanisms this plugin supports
  mechanisms:
    - sigstore-keyless
    - sigstore-key

  # Capabilities required
  capabilities:
    network: true # Requires network for Fulcio/Rekor
    keyStorage: false # Keyless mode
    environment:
      - SIGSTORE_REKOR_URL
      - SIGSTORE_FULCIO_URL
```

### Plugin Interface

#### Sign Operation

**Input Schema:**

```json
{
  "operation": "sign",
  "mechanism": "sigstore-keyless",
  "data": {
    "digest": "sha256:abc123...",
    "metadata": {
      "chart": "my-chart",
      "version": "1.0.0",
      "appVersion": "2.0.0"
    }
  },
  "options": {
    "identity": "release-bot@example.com",
    "oidcIssuer": "https://accounts.google.com",
    "rekorURL": "https://rekor.sigstore.dev",
    "fulcioURL": "https://fulcio.sigstore.dev"
  }
}
```

**Output Schema:**

```json
{
  "success": true,
  "signature": {
    "type": "sigstore-keyless",
    "data": "base64-encoded-signature...",
    "certificate": "base64-encoded-certificate...",
    "metadata": {
      "rekorLogIndex": 12345678,
      "rekorLogID": "abc123...",
      "signedTimestamp": "2026-02-28T12:00:00Z"
    }
  }
}
```

#### Verify Operation

**Input Schema:**

```json
{
  "operation": "verify",
  "mechanism": "sigstore-keyless",
  "data": {
    "digest": "sha256:abc123...",
    "metadata": {
      "chart": "my-chart",
      "version": "1.0.0"
    }
  },
  "signature": {
    "type": "sigstore-keyless",
    "data": "base64-encoded-signature...",
    "certificate": "base64-encoded-certificate...",
    "metadata": {
      "rekorLogIndex": 12345678
    }
  },
  "options": {
    "expectedIdentity": "release-bot@example.com",
    "expectedOIDCIssuer": "https://accounts.google.com",
    "rekorURL": "https://rekor.sigstore.dev"
  }
}
```

**Output Schema:**

```json
{
  "success": true,
  "verified": true,
  "details": {
    "identity": "release-bot@example.com",
    "issuer": "https://accounts.google.com",
    "signedAt": "2026-02-28T12:00:00Z",
    "transparencyLogVerified": true

}
```

#### Error Output

```json
{
  "success": false,
  "error": {
    "code": "VERIFICATION_FAILED",
    "message": "Certificate identity mismatch",
    "details": {
      "expected": "release-bot@example.com",
      "actual": "attacker@evil.com"
    }
  }
}
```

### Go SDK Interface

For SDK users leveraging the native Go plugin runtime (hip-plugin-go-runtime):

```go
// pkg/provenance/signer/interface.go

package signer

// Signer defines the interface for signing plugins.
type Signer interface {
    // Name returns the plugin identifier.
    Name() string

    // Mechanisms returns supported signing mechanisms.
    Mechanisms() []string

    // Capabilities returns required capabilities.
    Capabilities() Capabilities

    // Sign signs the given data.
    Sign(ctx context.Context, req *SignRequest) (*SignResponse, error)

    // Verify verifies a signature.
    Verify(ctx context.Context, req *VerifyRequest) (*VerifyResponse, error)
}

// SignRequest contains data to be signed.
type SignRequest struct {
    Mechanism string
    Digest    string
    Metadata  map[string]string
    Options   map[string]string
}

// SignResponse contains the signature.
type SignResponse struct {
    Signature   []byte
    Certificate []byte
    Metadata    map[string]string
}

// VerifyRequest contains data and signature to verify.
type VerifyRequest struct {
    Mechanism string
    Digest    string
    Signature []byte
    Certificate []byte
    SigMetadata map[string]string
    Options     map[string]string
}

// VerifyResponse contains verification results.
type VerifyResponse struct {
    Verified bool
    Identity string
    Issuer   string
    SignedAt time.Time
    Details  map[string]string
}

// Capabilities describes what the plugin needs.
type Capabilities struct {
    Network     bool
    KeyStorage  bool
    Environment []string
}
```

### SDK Registration

SDK users can register native Go implementations:

```go
import (
    "helm.sh/helm/v4/pkg/plugin"
    sigstoresigner "github.com/sigstore/helm-signer-sigstore"
)

func init() {
    // Register the Sigstore signer as native Go
    // This bypasses Wasm when running in SDK
    plugin.RegisterGoPlugin("signer/v1", "signer-sigstore",
        sigstoresigner.NewPlugin)
}
```

### Importable Go Packages

Official signer plugins are published as Go modules:

```go
// SDK user can import directly
import (
    gpgsigner "github.com/helm/helm-signer-gpg"
    sigsigner "github.com/sigstore/helm-signer-sigstore"
    notarysigner "github.com/notaryproject/helm-signer-notary"
)

// Use as library (bypassing plugin system entirely)
signer := sigsigner.New(sigsigner.Options{
    Keyless: true,
})
sig, err := signer.Sign(ctx, digest, metadata)
```

This allows:

1. **CLI users**: Use Wasm plugins (sandboxed)
2. **SDK users**: Register Go plugins (native performance)
3. **Library users**: Import directly (full control)

### Plugin Capabilities

Signer plugins declare required capabilities in `plugin.yaml`:

```yaml
signer:
  capabilities:
    # Network access for OIDC, transparency logs, etc.
    network: true

    # Access to key storage (keyring, HSM, etc.)
    keyStorage: true

    # Required environment variables
    environment:
      - SIGSTORE_REKOR_URL
      - GOOGLE_APPLICATION_CREDENTIALS

    # File system paths needed
    paths:
      - ~/.gnupg # GPG keyring
      - ~/.ssh # SSH keys
      - ~/.sigstore # Sigstore cache
```

Helm validates capabilities before invoking:

```go
// Before plugin invocation
if plugin.Capabilities.Network && !runtime.HasNetworkAccess() {
    return fmt.Errorf("plugin %s requires network access", plugin.Name)
}
```

### Auto-Detection

Helm auto-detects which signer to use based on signature type:

```go
func DetectSigner(sig *Signature) (Signer, error) {
    switch sig.Type {
    case "sigstore-keyless", "sigstore-key":
        return LoadPlugin("signer-sigstore")
    case "notary":
        return LoadPlugin("signer-notary")
    case "ssh":
        return LoadPlugin("signer-ssh")
    case "pgp", "gpg":
        return LoadPlugin("signer-gpg")
    default:
        return nil, fmt.Errorf("unknown signature type: %s", sig.Type)
    }
}
```

## Rationale

### Why Not Built-in Adapters?

The built-in approach (see alternative HIP) has trade-offs:

| Aspect                | Built-in         | Plugin         |
| --------------------- | ---------------- | -------------- |
| Initial simplicity    | ✓ Simpler        | More setup     |
| Long-term maintenance | Helm team burden | Distributed    |
| Binary size           | Grows            | Minimal core   |
| Update cycle          | Helm releases    | Independent    |
| Expertise             | Must learn all   | Domain experts |
| Community extensions  | Core PR required | Anyone         |

For security-critical code like signing, **expertise alignment** matters most. The Sigstore team understands cosign better than the Helm team ever will.

### Why Official Plugins?

Users must trust signing plugins. Official plugins provide:

1. **Organizational trust**: Published by reputable organizations
2. **Signature chain**: Plugins signed by their maintainers
3. **Audit trail**: Version history, security reviews
4. **Accountability**: Known team responsible for issues

### Why Go SDK Support?

The Go plugin runtime allows:

1. **Performance**: No Wasm overhead for SDK embedders
2. **Library reuse**: Import signing libraries directly
3. **Testing**: Mock signers without Wasm complexity
4. **Debugging**: Native Go stack traces

## Security Considerations

### Plugin Trust Model

Signer plugins are security-critical:

```
                    ┌─────────────────────────────┐
                    │   User trusts Helm          │
                    │         │                   │
                    │         ▼                   │
                    │   Helm trusts Official      │
                    │   Plugin Registry           │
                    │         │                   │
                    │         ▼                   │
                    │   Registry trusts Plugin    │
                    │   Maintainer (Sigstore)     │
                    │         │                   │
                    │         ▼                   │
                    │   Maintainer signs Plugin   │
                    │   with their key            │
                    └─────────────────────────────┘
```

### Wasm Sandboxing

CLI users run signer plugins in Wasm sandbox:

- **No filesystem access** except declared paths
- **No network** unless capability declared
- **No environment** except declared variables
- **Memory limits** enforced

### Native Go Trust

SDK users opting into native Go plugins accept:

- Full process permissions
- Their responsibility to audit
- Trust in Go module authenticity

## Example Implementations

### Sigstore Plugin (Go)

```go
// github.com/sigstore/helm-signer-sigstore

package sigstore

import (
    "context"

    "github.com/sigstore/cosign/v2/pkg/cosign"
    "github.com/sigstore/sigstore/pkg/fulcio"
    "helm.sh/helm/v4/pkg/provenance/signer"
)

type Plugin struct {
    rekorURL  string
    fulcioURL string
}

func NewPlugin(meta *plugin.Metadata) (plugin.Plugin, error) {
    return &Plugin{
        rekorURL:  getEnvOr("SIGSTORE_REKOR_URL", cosign.DefaultRekorURL),
        fulcioURL: getEnvOr("SIGSTORE_FULCIO_URL", fulcio.DefaultFulcioURL),
    }, nil
}

func (p *Plugin) Sign(ctx context.Context, req *signer.SignRequest) (*signer.SignResponse, error) {
    // Use cosign library to sign
    ko := cosign.KeyOpts{
        FulcioURL:    p.fulcioURL,
        RekorURL:     p.rekorURL,
        OIDCIssuer:   req.Options["oidcIssuer"],
        OIDCClientID: "sigstore",
    }

    sig, cert, err := cosign.SignBlob(ctx, ko, []byte(req.Digest), true)
    if err != nil {
        return nil, err
    }

    return &signer.SignResponse{
        Signature:   sig,
        Certificate: cert,
        Metadata: map[string]string{
            "rekorLogIndex": extractLogIndex(sig),
        },
    }, nil
}

func (p *Plugin) Verify(ctx context.Context, req *signer.VerifyRequest) (*signer.VerifyResponse, error) {
    // Use cosign library to verify
    co := cosign.CheckOpts{
        RekorURL:               p.rekorURL,
        CertIdentity:           req.Options["expectedIdentity"],
        CertOIDCIssuer:         req.Options["expectedOIDCIssuer"],
        IgnoreTlog:             false,
    }

    result, err := cosign.VerifyBlob(ctx, co, req.Signature, req.Certificate, []byte(req.Digest))
    if err != nil {
        return &signer.VerifyResponse{Verified: false}, nil
    }

    return &signer.VerifyResponse{
        Verified: true,
        Identity: result.Identity,
        Issuer:   result.Issuer,
        SignedAt: result.SignedAt,
    }, nil
}
```

## Rejected Alternatives

### 1. Built-in Adapters Only

While simpler initially, this burdens the Helm team with maintaining complex signing code and delays updates until Helm releases.

### 2. External Process Plugins

HashiCorp-style plugins using gRPC/HTTP were considered but add:

- Network overhead
- Process management complexity
- Platform-specific executables

Wasm provides better isolation with simpler distribution.

### 3. No Official Plugins

Leaving all plugins to community removes trust guarantees. Official plugins maintained by domain experts provide the trust foundation users need for security-critical code.
