## Abstract

This HIP proposes extending Helm's provenance system to support additional signing mechanisms beyond PGP, including Sigstore/cosign, Notary v2, and SSH signatures. The implementation uses a pluggable adapter pattern that allows new signing mechanisms to be added without modifying core Helm code.

## Motivation

### Current State

Helm has supported chart provenance signing since Helm 2 using PGP (GPG). While PGP provides strong cryptographic guarantees, adoption has been limited due to:

1. **Key management complexity**: GPG keyrings are notoriously difficult to manage
2. **No keyless options**: Every signature requires pre-distributed keys
3. **Air-gap friendly but network-unfriendly**: PGP works offline but lacks modern verification infrastructure
4. **Enterprise friction**: Many organizations have moved away from PGP for code signing

### Modern Alternatives

The signing landscape has evolved significantly:

| Mechanism | Keyless | Air-gap | OIDC | Transparency Log | Enterprise Adoption |
| --------- | ------- | ------- | ---- | ---------------- | ------------------- |
| GPG/PGP   | No      | Yes     | No   | No               | Declining           |
| Sigstore  | Yes     | Partial | Yes  | Yes              | Growing rapidly     |
| Notary v2 | No      | Yes     | No   | Optional         | Enterprise standard |
| SSH       | No      | Yes     | No   | No               | Developer-friendly  |

### Goals

1. Enable Sigstore/cosign signing for modern, keyless workflows
2. Support Notary v2 for enterprise OCI registry integration
3. Allow SSH key signing for developer convenience
4. Maintain backwards compatibility with existing GPG workflows
5. Design for future extensibility via plugin system

### Non-Goals

1. Deprecating GPG support
2. Mandating any specific signing mechanism
3. Implementing transparency log infrastructure (use existing services)

## Specification

### Signing Adapter Interface

Helm provenance will use a pluggable adapter pattern:

```go
// pkg/provenance/adapter.go

// SigningAdapter provides signing and verification for a specific mechanism.
type SigningAdapter interface {
    // Name returns the adapter identifier (e.g., "pgp", "sigstore", "notary", "ssh")
    Name() string

    // Sign signs the given data and returns the signature.
    Sign(data []byte, options SignOptions) (*Signature, error)

    // Verify verifies a signature against the given data.
    Verify(data []byte, sig *Signature, options VerifyOptions) (*VerifyResult, error)

    // SupportsKeyless returns true if the adapter supports keyless signing.
    SupportsKeyless() bool

    // RequiresNetwork returns true if verification requires network access.
    RequiresNetwork() bool
}

// Signature represents a cryptographic signature.
type Signature struct {
    // Type identifies the signing mechanism (e.g., "pgp", "cosign", "notary", "ssh")
    Type string

    // Data contains the signature bytes
    Data []byte

    // Metadata contains mechanism-specific information
    Metadata map[string]string
}
```

### Supported Mechanisms

#### 1. Sigstore/Cosign

Sigstore provides keyless signing using OIDC identity:

```bash
# Sign with Sigstore (keyless - uses OIDC)
helm package my-chart/ --sign=sigstore

# Sign with Sigstore (with key)
helm package my-chart/ --sign=sigstore --key cosign.key

# Verify
helm verify my-chart-1.0.0.tgz --keyless
helm verify my-chart-1.0.0.tgz --certificate-identity user@example.com \
    --certificate-oidc-issuer https://accounts.google.com
```

**Implementation notes:**

- Uses [sigstore/cosign](https://github.com/sigstore/cosign) Go library
- Supports Rekor transparency log
- Keyless mode requires network for signing and verification
- Key-based mode works offline for verification

#### 2. Notary v2 (OCI Signatures)

Notary v2 stores signatures as OCI artifacts alongside charts:

```bash
# Sign with Notary v2
helm package my-chart/ --sign=notary --key my-signing-key

# Push with signature
helm push my-chart-1.0.0.tgz oci://registry.example.com/charts

# Verify (automatic when pulling from OCI)
helm pull oci://registry.example.com/charts/my-chart --version 1.0.0 --verify
```

**Implementation notes:**

- Uses [notation-go](https://github.com/notaryproject/notation-go) library
- Signatures stored as OCI artifacts (referrers API)
- Native integration with OCI registries
- Supports trust policies and certificate chains

#### 3. SSH Signatures

SSH signatures use existing SSH keys developers already have:

```bash
# Sign with SSH key
helm package my-chart/ --sign=ssh --key ~/.ssh/id_ed25519

# Verify with allowed signers file
helm verify my-chart-1.0.0.tgz --ssh-allowed-signers ~/.ssh/allowed_signers
```

**Implementation notes:**

- Uses Go's `crypto/ssh` package
- Format compatible with `git` SSH signatures
- Leverages existing SSH key infrastructure
- Simple for developers, no new key types needed

#### 4. PGP/GPG (Existing)

Existing PGP support remains unchanged:

```bash
# Sign with GPG (current behavior)
helm package my-chart/ --sign --key user@example.com

# Verify
helm verify my-chart-1.0.0.tgz --keyring ~/.gnupg/pubring.gpg
```

### Provenance File Format

The `.prov` file format is extended to support multiple signature types:

```yaml
# Current format (PGP only)
-----BEGIN PGP SIGNED MESSAGE-----
Hash: SHA512
...chart metadata...
-----BEGIN PGP SIGNATURE-----
...signature data...
-----END PGP SIGNATURE-----
```

```yaml
# Extended format (new signatures)
---
apiVersion: helm.sh/provenance/v1
kind: Provenance
metadata:
  chart: my-chart
  version: 1.0.0
  digest: sha256:abc123...
signature:
  type: sigstore # or: notary, ssh, pgp
  data: |
    ...base64 encoded signature...
  metadata:
    # Sigstore-specific
    certificate: |
      ...x509 certificate...
    rekorLogIndex: 12345
    # Notary-specific
    ociReference: registry.example.com/charts/my-chart@sha256:abc123

    # SSH-specific
    signer: user@example.com
```

### CLI Changes

#### `helm package`

```bash
helm package my-chart/ [flags]

Signing Flags:
  --sign              Sign the package (default mechanism from config)
  --sign=TYPE         Sign using specific mechanism: pgp, sigstore, notary, ssh
  --key KEY           Signing key (path, ID, or identity depending on mechanism)
  --keyring PATH      Keyring file (PGP only)
  --no-sign           Explicitly skip signing (for v3 charts)
  --keyless           Use keyless signing (Sigstore only)
```

#### `helm verify`

```bash
helm verify CHART [flags]

Verification Flags:
  --keyring PATH              PGP keyring file
  --keyless                   Allow keyless Sigstore signatures
  --certificate-identity ID   Expected identity for Sigstore certificates
  --certificate-oidc-issuer   Expected OIDC issuer for Sigstore
  --ssh-allowed-signers PATH  SSH allowed signers file
  --trust-policy PATH         Notary trust policy file
```

### Configuration

Default signing mechanism can be configured:

```yaml
# ~/.config/helm/config.yaml
signing:
  default: sigstore # Default mechanism for --sign flag
  sigstore:
    rekorURL: https://rekor.sigstore.dev
    fulcioURL: https://fulcio.sigstore.dev
  notary:
    trustPolicy: ~/.config/helm/trust-policy.json
  ssh:
    allowedSigners: ~/.ssh/helm_allowed_signers
```

### Trust Management Integration

This HIP integrates with the trust management system (see chart-defined plugins trust workflow):

```yaml
# ~/.config/helm/trusted-keys.yaml
keys:
  - name: "My Organization"
    type: sigstore
    identity: "release-bot@example.com"
    issuer: "https://accounts.google.com"
    scope: all

  - name: "Enterprise CA"
    type: notary
    certificateChain: |
      -----BEGIN CERTIFICATE-----
      ...
      -----END CERTIFICATE-----
    scope: charts

  - name: "Developer Key"
    type: ssh
    publicKey: "ssh-ed25519 AAAA..."
    scope: plugins
```

## Rationale

### Plugin Architecture vs Built-in

We considered making signing mechanisms pluggable via external plugins (like `provenance/v1` plugin type). However:

**Pros of built-in adapters:**

- Simpler user experience
- No additional installation
- Consistent behavior across environments

**Pros of plugin architecture:**

- Easier to add new mechanisms
- Community can contribute without core changes
- Lighter core binary

**Decision:** Start with built-in adapters for the four primary mechanisms. Consider plugin extensibility in a future HIP if demand warrants.

### Why These Four Mechanisms?

1. **PGP**: Backwards compatibility, air-gap support
2. **Sigstore**: Modern keyless signing, growing ecosystem adoption
3. **Notary v2**: Enterprise OCI workflow integration
4. **SSH**: Developer convenience, zero new tooling

### Provenance File Versioning

The new provenance format uses `apiVersion: helm.sh/provenance/v1` to distinguish from legacy PGP-only format. Helm will auto-detect format based on content.

## Backwards Compatibility

- Existing PGP workflows unchanged
- Legacy `.prov` files continue to work
- New flags are additive
- Default behavior unchanged unless explicitly configured

## Security Considerations

### Threat Model

Each mechanism has different security properties:

| Threat               | PGP          | Sigstore           | Notary v2   | SSH             |
| -------------------- | ------------ | ------------------ | ----------- | --------------- |
| Key compromise       | Revocation   | Certificate expiry | CRL/OCSP    | Manual          |
| Replay attacks       | Timestamp    | Rekor log          | OCI digest  | None            |
| Impersonation        | Web of trust | OIDC identity      | X.509 chain | Allowed signers |
| Air-gap verification | Yes          | Partial\*          | Yes         | Yes             |

\*Sigstore keyless requires network for transparency log verification.

### Key Management

Each mechanism has different key management:

- **PGP**: User manages keyring
- **Sigstore**: OIDC identity (keyless) or cosign-generated keys
- **Notary v2**: X.509 certificates, potentially from enterprise CA
- **SSH**: Existing SSH keys

## Implementation Plan

### Phase 1: Core Infrastructure

- Define `SigningAdapter` interface
- Implement adapter registry
- Update provenance file format parser

### Phase 2: Adapter Implementation

- Implement Sigstore adapter (cosign library)
- Implement SSH adapter (crypto/ssh)
- Update PGP adapter to interface

### Phase 3: Notary v2 Integration

- Implement Notary adapter
- OCI referrers API integration
- Trust policy support

### Phase 4: Trust Management

- Unified trusted-keys.yaml format
- Integration with chart-defined plugins trust
- TOFU mode for all mechanisms

## Rejected Alternatives

### Sigstore Only

Mandating Sigstore would exclude air-gapped environments and break backwards compatibility.

### External Plugin System

While appealing, external plugins add complexity and potential security risks for cryptographic operations.

### Separate Commands per Mechanism

Having `helm sigstore-sign`, `helm ssh-verify`, etc. fragments the UX. A unified interface with mechanism flags is cleaner.

## Open Issues

1. **Should Sigstore be the recommended default for new projects?**
   - It has the best UX (keyless) and security properties (transparency log)
   - But requires network access

2. **How to handle multiple signatures?**
   - Some workflows may want both PGP (air-gap) and Sigstore (transparency)
   - Should `.prov` support multiple signatures?

3. **Notary v2 trust policy complexity**
   - Notation's trust policy format is powerful but complex
   - Should Helm provide a simplified wrapper?
