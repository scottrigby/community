## Abstract

This HIP proposes adding a native Go runtime option for Helm plugins, allowing SDK users to satisfy plugin invocations with Go code directly rather than going through Wasm compilation.

## Motivation

The current Helm 4 plugin system (HIP-0026) uses Wasm as the universal plugin format, compiled to native machine code at runtime via Wazero. While this provides excellent portability and security isolation, SDK users may want to use native Go implementations directly for certain plugin types.

**The problem:**

1. Go source code is compiled to Wasm binary
2. Wasm binary is distributed via OCI
3. At runtime, Wasm is JIT-compiled to native machine code
4. Native machine code is executed

For SDK users who are already running Go, steps 1-3 add overhead:

- Build complexity (Go → Wasm toolchain)
- Distribution size (Wasm binaries are larger than Go source)
- Runtime cost (JIT compilation, even with caching)

**Proposed solution:**

Allow SDK users to register native Go implementations for plugin types, bypassing the Wasm layer entirely when appropriate.

## Specification

### New Runtime Type: `go/v1`

Add a new runtime type alongside existing runtimes:

```go
// Current runtimes
"subprocess"  // Legacy CLI plugins
"extism/v1"   // Wasm plugins via Extism/Wazero

// New runtime
"go/v1"       // Native Go plugins (SDK only)
```

### Runtime Interface

The existing `Runtime` interface remains unchanged:

```go
type Runtime interface {
    CreatePlugin(pluginPath string, metadata *Metadata) (Plugin, error)
}
```

A new `RuntimeGo` implementation would satisfy this interface:

```go
type RuntimeGo struct {
    // Registry of native Go plugin implementations
    Plugins map[string]GoPluginFactory
}

type GoPluginFactory func(metadata *Metadata) (Plugin, error)
```

### SDK Registration API

SDK users register native Go implementations:

```go
import "helm.sh/helm/v4/pkg/plugin"

// Register a native Go render plugin
plugin.RegisterGoPlugin("render/v1", "gotemplate-render", func(m *plugin.Metadata) (plugin.Plugin, error) {
    return &myGotemplatePlugin{}, nil
})

// Register a native Go getter plugin
plugin.RegisterGoPlugin("getter/v1", "s3", func(m *plugin.Metadata) (plugin.Plugin, error) {
    return &myS3Plugin{}, nil
})
```

### Plugin Resolution Order

When resolving a plugin, Helm SDK checks in order:

1. **Registered Go plugins** (if `go/v1` runtime enabled)
2. **Wasm plugins** (default, via `extism/v1` runtime)

This allows SDK users to override specific plugins while falling back to Wasm for others.

### Use Cases

**1. K8s Controllers**

Controllers using the Helm SDK could register native Go implementations for common plugins:

```go
// In helm-controller initialization
plugin.RegisterGoPlugin("render/v1", "gotemplate-render", newNativeGotemplateRenderer)
```

Benefits:

- Zero Wasm overhead for gotemplate rendering
- Smaller memory footprint
- Faster startup (no JIT compilation)

**2. Helm SDK Embedders**

Custom Helm SDK users could provide optimized implementations:

```go
// Custom high-performance renderer
plugin.RegisterGoPlugin("render/v1", "fast-yaml", newOptimizedYAMLRenderer)
```

**3. Testing**

Mock plugins for testing without Wasm:

```go
// In test setup
plugin.RegisterGoPlugin("render/v1", "test-render", newMockRenderer)
```

## Security Considerations

### Wasm Sandboxing vs Native Code

- **Wasm plugins**: Run in Wazero sandbox with restricted capabilities
- **Go plugins**: Run with full process permissions

SDK users who register native Go plugins take responsibility for:

- Code review and trust verification
- Capability restrictions (if any)
- Security implications of running native code

### CLI vs SDK

- **CLI users**: Always use Wasm plugins (sandboxed)
- **SDK users**: Opt-in to native Go plugins (their responsibility)

This maintains security for CLI users while giving SDK users flexibility.

## Backwards Compatibility

This proposal is fully backwards compatible:

- No changes to existing Wasm plugin format
- No changes to Chart.yaml plugin syntax
- SDK users who don't register Go plugins see no difference
- CLI behavior unchanged (always uses Wasm)

## Rejected Alternatives

### 1. Go Plugin Packages (`plugin.Open`)

Go's built-in plugin system was considered but rejected:

- Requires CGO
- Platform-specific .so/.dylib files
- Version compatibility issues between plugin and host

### 2. Shared Libraries

Native shared libraries were considered but rejected:

- Platform-specific compilation
- Complex distribution
- ABI compatibility concerns

### 3. gRPC/HTTP Plugin Protocol

HashiCorp-style plugin protocol was considered:

- Adds network overhead
- More complex than direct function calls
- Overkill for embedded SDK use case
