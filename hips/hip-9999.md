## Abstract

This H4HIP proposes a unified enhanced trust workflow for Helm 4 that applies consistently to both chart packages and chart-defined plugins. It covers:

1. **Default signing and verification for Chart API v3**: `helm package` signs by default; `helm install`, `helm upgrade`, and `helm template` verify by default
2. **Default verification for chart-defined plugins**: `helm dependency update` verifies plugin provenance by default, using the existing keyring mechanism
3. **ArtifactHub as an additional key source**: Helm can optionally fetch publisher public keys from ArtifactHub to supplement the local keyring — with graceful failure for airgap environments
4. **Trusted publishers management**: A config-driven workflow so users and CI environments can approve publishers once rather than per-artifact

These improvements use and extend Helm's existing provenance and keyring infrastructure rather than replacing it.

## Motivation

Helm has supported chart provenance signing since Helm 2, but adoption has been limited because verification is opt-in and key management is manual. As a result, chart and plugin provenance is rarely verified in practice.

Chart API v3 and chart-defined plugins (introduced in Helm 4) provide a clean opportunity to establish better security defaults from day one. Since no v3 charts or chart-defined plugins exist yet in the wider ecosystem, there are no backwards-compatibility concerns for users who have not yet adopted these features.

Additionally, the two trust problems — chart verification and plugin verification — share the same root causes (opt-in verification, key management burden) and are best addressed with a unified design. Solving them separately would risk inconsistent UX or duplicated infrastructure.

## Specification

### 1. Default signing for Chart API v3

`helm package` signs Chart API v3 charts by default. The existing `--sign` flag is reused; for v3 charts its default-when-omitted changes from `false` to `true`.

```bash
# Chart API v2 (unchanged)
helm package my-v2-chart/                    # Does not sign (--sign defaults false)
helm package my-v2-chart/ --sign             # Signs (opt-in, same as today)

# Chart API v3 (new defaults)
helm package my-v3-chart/ --key <key-id>     # Signs (default for v3)
helm package my-v3-chart/ --sign=false       # Explicit opt-out (prints warning)
```

When `--sign=false` is used with a v3 chart:

```
WARNING: Chart packaged without provenance signature. Unsigned charts
may be rejected by consumers with verification enabled.
```

### 2. Default verification for Chart API v3

`helm install`, `helm upgrade`, and `helm template` verify Chart API v3 chart provenance by default. The existing `--verify` and `--keyring` flags are reused.

```bash
# Chart API v2 (unchanged)
helm install my-release my-v2-chart/         # Does not verify (--verify defaults false)
helm install my-release my-v2-chart/ --verify  # Verifies (opt-in, same as today)

# Chart API v3 (new defaults)
helm install my-release my-v3-chart/                       # Verifies (default for v3)
helm install my-release my-v3-chart/ --keyring <path>      # Verifies with custom keyring
helm install my-release my-v3-chart/ --verify=false        # Explicit opt-out (prints warning)
```

Verification uses the user's default keyring or the path specified by `--keyring`. Note: `--keyring` replaces the default keyring path entirely — it does not merge with it. If you need keys from both your default keyring and a custom path, load them into a single keyring file first.

When `--verify=false` is used with a v3 chart:

```
WARNING: Installing chart without provenance verification. This bypasses supply chain security.
```

### 3. Default verification for chart-defined plugins

`helm dependency update` verifies chart-defined plugin provenance by default, using the same mechanism as subchart verification. Plugin publishers publish a `.prov` file alongside the plugin OCI artifact. The existing `--keyring` flag applies.

```bash
# Chart-defined plugin verification (default on for v3 charts)
helm dependency update ./my-chart/                    # Verifies plugins (default)
helm dependency update ./my-chart/ --keyring <path>   # Verifies with custom keyring
helm dependency update ./my-chart/ --verify=false     # Explicit opt-out (prints warning)
```

Note: `helm package -u` (subchart dependency update before packaging) does not download or verify chart-defined plugins. Plugins are runtime dependencies, never embedded in a packaged chart.

### 4. ArtifactHub as an additional key source

To reduce key management burden, Helm can optionally query ArtifactHub to discover and fetch a publisher's signing public key, adding it to a Helm-managed local keyring.

```
helm key fetch --from-artifacthub <org>/<plugin-name>
```

This command:

1. Queries the ArtifactHub API for the publisher's signing key
2. Displays the key fingerprint for user confirmation
3. Stores the key in `$HELM_CONFIG_HOME/trusted-keys/`

Helm uses the `trusted-keys/` directory as an additional keyring alongside the default or `--keyring`-specified keyring when verifying signatures.

**Airgap support**: ArtifactHub key fetching is always supplemental and never required. If ArtifactHub is unreachable (e.g., in an airgap environment), Helm logs a debug message and proceeds with whatever keys are already in the local keyring. Verification succeeds or fails based solely on locally available keys.

```bash
# Airgap environments: pre-import keys before going offline
helm key fetch --from-artifacthub example-org/my-plugin
# ... then operate offline; ArtifactHub unreachability is non-fatal
```

### 5. Trusted publishers config

A config file at `$HELM_CONFIG_HOME/trusted-publishers.yaml` stores publisher identities that have been approved, so users are not prompted on every download.

```yaml
publishers:
  - name: Example Org
    artifacthub_org: example-org
    fingerprints:
      - "ABCD 1234 EF56 7890"
```

Publishers can be added interactively during `helm dependency update` (prompted when a new publisher is encountered) or explicitly:

```bash
helm trust add example-org/my-plugin   # Add publisher from ArtifactHub
helm trust list                         # List trusted publishers
helm trust remove example-org           # Remove publisher
```

**CI environments**: Pre-populate `$HELM_CONFIG_HOME/trusted-publishers.yaml` before running `helm dependency update`. No interactive prompts are shown for pre-approved publishers.

### 6. Trust-on-first-use (TOFU)

When Helm encounters a new publisher whose key is available (in keyring or fetchable from ArtifactHub), it can prompt the user to trust the key fingerprint on first use:

```
Plugin verification for my-plugin v1.0.0:
  Publisher: Example Org (verified on ArtifactHub)
  Key fingerprint: ABCD 1234 EF56 7890

Trust this publisher?
  y = yes, trust for this download only
  N = no, reject
  t = trust publisher, save to trusted-publishers.yaml

Choice [y/N/t]:
```

Choosing `t` saves the publisher to `trusted-publishers.yaml` so future downloads are silent.

## Rationale

### Why default-on for v3 only?

Chart API v2 has an established ecosystem of unsigned charts. Requiring verification for v2 would break virtually every Helm deployment. Chart API v3 is still experimental in Helm 4, so no existing v3 charts exist — making default-on verification safe from day one.

### Why reuse existing `--sign` and `--verify` flags?

Introducing `--no-sign` and `--no-verify` as new flags would mean maintaining two ways to express the same thing. Changing the default-when-omitted for v3 charts is cleaner and requires only a help text update.

### Why ArtifactHub as supplemental, not primary?

Making ArtifactHub required for verification would break airgap deployments and introduce a network dependency on a third-party service. ArtifactHub key fetching is a convenience feature layered on top of the existing GPG keyring mechanism, not a replacement for it.

### Why a unified HIP rather than separate proposals?

Charts and plugins share the same root cause (opt-in verification, key management burden) and benefit from the same solution (default verification, ArtifactHub supplemental keys, trusted publishers config, TOFU). A unified design ensures consistent UX and avoids duplicated infrastructure.

## Backwards Compatibility

This proposal is fully backwards compatible within Helm 4:

| Scenario           | v2 (unchanged) | v3 (new)                  |
| ------------------ | -------------- | ------------------------- |
| `--sign` omitted   | do not sign    | sign by default           |
| `--sign` present   | sign           | sign                      |
| `--sign=false`     | do not sign    | do not sign (+ warning)   |
| `--verify` omitted | do not verify  | verify by default         |
| `--verify` present | verify         | verify                    |
| `--verify=false`   | do not verify  | do not verify (+ warning) |

Chart API v3 is still experimental in Helm 4, so changing its defaults is not a breaking change within the major version.

## Security implications

### Airgap and offline environments

ArtifactHub key fetching is entirely optional and fails gracefully. Helm never requires a network connection for verification — it only requires keys to be locally available (in the default keyring, `--keyring` path, or `$HELM_CONFIG_HOME/trusted-keys/`).

### Key management

This proposal does not change the underlying GPG provenance mechanism. The same threat model applies: signing proves authorship, not intent. Key compromise is handled by standard GPG key rotation practices.

### `--verify=false` and `--sign=false`

These flags exist as last-resort escapes for environments that cannot use signed artifacts. When used with v3 charts or plugins, Helm prints a prominent warning. Plugin authors and chart distributors are strongly encouraged to sign their releases. If an upstream artifact is unsigned, the consuming party should re-sign and re-distribute rather than disabling verification.

## How to teach this

- Update `helm package`, `helm install`, `helm upgrade`, and `helm dependency update` help text to document the v2/v3 flag default difference
- Add a Helm documentation page on key management and trusted publishers
- Update ArtifactHub documentation to encourage plugin and chart authors to publish signing keys

## Rejected ideas

### ArtifactHub as required verification mechanism

Making ArtifactHub the primary verification method (rather than supplemental) would break airgap environments and introduce a required network dependency.

### Separate HIPs for charts and plugins

The trust problems for charts and plugins are identical in nature. Separate HIPs would risk inconsistent UX and duplicated infrastructure. A unified approach produces a simpler, more coherent system.

### New `--no-sign` and `--no-verify` flags

Reusing existing `--sign` and `--verify` flags (changing only their default for v3) is cleaner than introducing new flags for the same purpose.

## Open issues

1. **`helm key fetch` command scope**: Should key fetching be a standalone command or integrated into `helm dependency update`/`helm install` automatically (with opt-in)?

2. **Multiple keyring merging**: The current behavior is that `--keyring` replaces the default keyring path entirely. Should Helm support merging multiple keyring sources in a future enhancement?

3. **`--keyring` for OCI-hosted artifacts**: The current provenance mechanism uses `.prov` sidecar files. For OCI artifacts (plugins, OCI-stored charts), the mechanism for publishing and discovering `.prov` files needs definition.
